# Hishabi — Database Schema

**Target:** PostgreSQL · SQLAlchemy 2.0 typed ORM · Alembic migrations
**Domain:** Inventory / product management

---

## 1. Overview

Hishabi manages products, categories, users with roles, and stock movements, with an audit trail
recording who changed what.

### Conventions

| Concern | Convention |
|---|---|
| Primary keys | `INTEGER` — never UUID. `GENERATED BY DEFAULT AS IDENTITY` |
| Timestamps | `TIMESTAMP` with `server_default=func.now()` |
| Money | `NUMERIC(12,2)` — never floating point |
| Quantity | `NUMERIC(12,3)` — never floating point |
| Currency | BDT (Bangladeshi Taka) |
| Foreign keys | Every FK declares an explicit `ON DELETE` behaviour |
| JSONB | Used for before/after snapshots in `audit_logs` |

## 4. Foreign Keys

| Foreign key | References | ON DELETE | Reasoning |
|---|---|---|---|
| `users.role_id` | `roles.id` | SET NULL | Removing a role must not delete the accounts that hold it; the user stays and is reassigned or deactivated |
| `products.category_id` | `categories.id` | CASCADE | A product cannot exist without a category; deleting the category removes its products |
| `stock_movements.product_id` | `products.id` | CASCADE | A movement is meaningless without its product; deleting the product removes its movements |
| `stock_movements.user_id` | `users.id` | SET NULL | History survives user deletion, keeping the ledger intact |
| `audit_logs.user_id` | `users.id` | SET NULL | Audit records are permanent evidence and must outlive the user |

**User deletion.** Users are deactivated (`is_active = false`) rather than hard-deleted, so
`stock_movements` and `audit_logs` keep their referential history.

**Audit history.** `audit_logs` rows are never deleted by a cascading FK, preserving the
change trail independently of the entities they describe.

## 7. Implementation Notes

### 7.1 SQLAlchemy 2.0 style

Models use typed `Mapped[]` / `mapped_column()` declarations against a shared `DeclarativeBase`
defined in `app/core/database.py`:

```python
class Base(DeclarativeBase):
    pass


class TimestampMixin:
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=False), server_default=func.now(), nullable=False
    )
    updated_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=False),
        server_default=func.now(),
        onupdate=func.now(),
        nullable=False,
    )
```

Points to observe:

1. **Identity primary keys.** `mapped_column(Integer, Identity(always=False), primary_key=True)`
   generates `GENERATED BY DEFAULT AS IDENTITY`. `ALWAYS` would block client-supplied ids, which
   imports and seed scripts often need.
2. **Timestamps** are server-generated through `server_default=func.now()`. Python-side
   `datetime.now()` is reserved for transient values, so the database stays the single clock
   source. `updated_at` uses `onupdate=func.now()`, which SQLAlchemy emits on ORM-level updates
   only — bulk `Core` statements must set it explicitly.
3. **`ON DELETE` is declared on every `ForeignKey`** in the ORM so the generated DDL matches the
   specification in §4.
4. **`JSONB` columns** map to `Mapped[dict | None]` with the Postgres dialect type
   `sqlalchemy.dialects.postgresql.JSONB`.

### 7.2 Money and quantity

All monetary and quantity columns use `Numeric`, never `Float`. Binary floating point cannot
represent values like `0.1` exactly, so summing float amounts across many rows silently corrupts
totals.

- `NUMERIC(12,2)` for `purchase_price` and `sale_price` — exact base-10, two decimal places.
- `NUMERIC(12,3)` for `current_stock`, `low_stock_threshold`, `quantity`, `balance_after` —
  three decimal places allow fractional stock such as kilograms.
- The ORM type is `Numeric(12, 2, asdecimal=True)`, producing Python `decimal.Decimal`.
  Amounts are never annotated or handled as `float`.
- All arithmetic happens in `Decimal`. Rounding occurs only at the serialization boundary, using
  `quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)` — never mid-calculation.
- `func.sum(products.sale_price)` returns a `Decimal` on Postgres. Cast in SQL if a float ever
  enters the expression: `func.sum(...).cast(Numeric(12, 2))`.

**Serialization.** Pydantic v2 serialises `Decimal` to a JSON **string** by default — verified
against the installed `pydantic 2.14.3`, where `Decimal("1234.56")` emits `"1234.56"`. This is the
desired behaviour: converting to a JSON number reintroduces binary float drift on the client, and
JavaScript's `Number` cannot represent all cent values exactly. The frontend parses with
`Number()` for display (safe within `Number.MAX_SAFE_INTEGER`) or uses a decimal-aware formatter.

### 7.3 Currency

All monetary amounts are denominated in **BDT**. There is no per-row currency column — amounts
in `products.purchase_price`, `products.sale_price`, and any computed total are BDT by
convention. If multi-currency support is added later, it requires a `currency` column with an
ISO 4217 code and a conversion-rate table.

### 7.4 Enumerated columns

`movement_type`, `action`, `reference_type`, and `entity_type` are `VARCHAR` columns. Values are
validated in the Pydantic layer with `Literal` types, which return a `422` before the database is
reached. Native Postgres `ENUM` types are avoided: `ALTER TYPE ... ADD VALUE` cannot run inside a
transaction on older PostgreSQL versions and Alembic's autogenerate does not detect added enum
values, producing silent schema drift.

### 7.5 Stock movement direction

`stock_movements.movement_type` carries the business reason for the movement, and
the direction of the change follows from it:

| `movement_type` | Effect on `current_stock` | `quantity` sign |
|---|---|---|
| `purchase` | increases | must be positive |
| `return` | increases — goods coming back from a customer | must be positive |
| `sale` | decreases | must be positive |
| `adjustment` | depends | signed: negative decreases, positive increases |

An `adjustment` is the only movement that may carry a negative quantity, and
only an owner may post one. A movement is rejected with a `400` when it would
leave `current_stock` below zero.

## 9. Assumptions

The schema was supplied as a fixed column list. The following decisions were taken where the
specification was silent, and are recorded here so they can be reviewed and changed in one place:

1. **Nullability.** Columns with an explicit `NOT NULL` are enforced as such. Columns without one
   are nullable except where a default makes them effectively always present (`is_active`,
   `current_stock`, `low_stock_threshold`, `purchase_price`, `created_at`, `updated_at`).
2. **`ON DELETE` behaviour.** Chosen per the rationale in §4. The notable one is
   `products.category_id` → CASCADE, meaning deleting a category deletes its products; if
   products should survive a category deletion, change this to `RESTRICT` and soft-delete
   categories instead.
3. **Identity columns.** `INTEGER ... GENERATED BY DEFAULT AS IDENTITY` rather than `SERIAL`.
   Both are valid, but identity is the modern standard and behaves better with concurrent inserts.
4. **Timestamp type.** `TIMESTAMP WITHOUT TIME ZONE`, matching the specification. Server-side
   `now()` therefore returns local server time. If the deployment runs across timezones, switch to
   `TIMESTAMPTZ`.
5. **`users.role_id` is nullable.** A user can exist before a role is assigned.
6. **`audit_logs.entity_id` has no foreign key.** It intentionally spans multiple entity types, so
   a FK is not possible; `entity_type` supplies the discriminator.
7. **`stock_movements.balance_after` is denormalised.** It stores the stock level at the moment of
   the movement so a product's history can be reconstructed without recomputation.
